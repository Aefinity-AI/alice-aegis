## Corpus

Five attack families × six cases, all against the real in-repo M7 artifacts
(`model-lab/tinybit/m7_final_gate_work/artifacts/`, sha256 pinned in the raw log) and either the
vendored golden receipt or receipts minted in-test by driving `cis-verify`'s own engine and
retaining each step's complete i64 logit vector — which is what lets the B/D/E families re-fold a
witness chain that is **internally perfectly self-consistent** over falsified values. Nothing here
is random fuzz; that is E19's job.

`E20 result: 30/30 rejected with a pre-registered field`

**The E family is the load-bearing half.** Every E case keeps the *real* token ids and therefore
the real `cis-digest`: tokens agree, the FNV digest agrees, and only the full-logit chain can see
that a cheaper numeric path produced the committed values. All six pre-registered `chain` exactly
— no alternatives — and all six fired `chain`. That is the empirical case for committing to
logits rather than tokens: a token-only receipt would have accepted all six.

Likewise C15 and D20–D22 are the cases an attacker who *owns the model* can actually construct: a
flawlessly self-consistent receipt over falsified or substituted inputs. They are caught by
replay, not by internal consistency, which is the whole architecture of the verifier.

## Corrections made during the run (reported because they read as bypasses)

Both were flaws in *my* case construction. Recording them because "the verifier accepted it" and
"the claim was actually true" are easy to confuse, and the fix generalises.

1. **First-draft E27** committed logits clamped into `i32` range as a "32-bit accumulator
   downgrade". Measured M7 logit range over the 12 witnessed steps is `min -193845165 /
   max 99899727`, entirely inside `i32` — so the clamp was a no-op and the "forged" receipt was
   byte-identical to the honest one. Correct acceptance. Replaced with the one-hot
   (argmax-only-commitment) case, which does change every committed value.
2. **First-draft D22** mutated 256 bytes at the midpoint of VOCAB.BIN. The M7 string table ends at
   byte 68730 of 163954, so the mutation landed in the merges table, in entries the prompt never
   uses: a genuinely different file that computes the same thing, whose receipt is therefore
   genuinely valid. Correct acceptance. Replaced with a targeted rewrite of the string-table
   record for the single-character token the prompt's first byte maps through.

Two guards now make this class of mistake fail loudly instead of reading as a bypass:
`assert_substitution_is_material()` mints an honest receipt for each substituted artifact triple
and asserts the crafted receipt differs from it, and every pristine-artifact case is asserted
different from both the honest and the golden receipt. A third test,
`e20_degenerate_case_measurements`, is the Rule-B provenance for the two measurements quoted above
(logit range, VOCAB.BIN string-table extent) and fails if either premise stops holding.

A third correction: `FOREIGN_MODEL_SHA` (case A04) was initially written from memory of a ledger
row and was **wrong past its first 8 hex digits**. It is now the exact `model` line of
`tests/golden/witness_v1_bitnet2b_once64.receipt`, and a new test
(`foreign_model_sha_matches_the_2b_golden_receipt`) re-checks the pinned constant against that file
whenever the full repo is present.

## Documented gap (not a bypass; no verified quantity is affected)

`AEGIS-WITNESS v1-CIS` has **no `mode` field**, and unknown keys are ignored by design
(`receipt.rs`, mirroring `cis_witness.rs:191`). Nothing outside the ten known fields is bound by
the witness chain, so a receipt carrying `mode hybrid` or `attested-by <anyone>` still verifies —
the verifier never looked at those lines. Every *computational* claim (artifacts, prompt, token
stream, full logit chain) remains bound; families B and E prove that. Recorded as
`e20_unknown_receipt_lines_are_not_bound_by_the_chain`, which asserts the current behaviour so a
future format change is a deliberate, visible one.

Recommendation (normative, so Justin's call): if the receipt format ever grows a `mode`, a
`spec-version`, or any other semantic field, it must be folded into the witness header, not added
as another ignored line. A reader who sees `mode fullint` on a receipt today will believe the
verifier checked it. It did not.

## Scope deviation from the plan text

The plan names "the known-good A39/A44 receipts". A39's receipt is bound to the BitNet-2B triple
(MODEL.SAF 522,831,917 B + EMBED.BIN 257,310,720 B); replaying it locally exceeds this leg's
light-lane RSS budget (~400 MB) while other legs hold the box. The corpus therefore uses the M7
golden receipt (same format, same verifier code path, artifacts in-repo at ~9 MB) as its
known-good baseline, and the 2B receipt only as the source of the real foreign artifact hash in
A04. A44 is a cross-ISA active-set digest gate, not a receipt, so there is nothing there to
accept or reject. Re-running this corpus against the 2B artifacts is a heavy-lane or CI follow-up
and needs no code change — only a different artifact path.
