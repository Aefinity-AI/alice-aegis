## What was done

1. `cargo install cargo-fuzz --locked` (was not installed; nightly toolchain was already present) — succeeded, `cargo-fuzz 0.13.2`.
2. `cargo fuzz init` in `cis-verify/`, then wrote three real targets (the placeholder `fuzz_target_1.rs` removed):
   - `fuzz_targets/receipt_parser.rs` — feeds arbitrary (UTF-8-filtered) bytes into `cis_verify::receipt::Receipt::parse`.
   - `fuzz_targets/witness_chain.rs` — decodes a fixed byte layout (header fields + a run of token-id/logit-vector steps) and drives `WitnessHeader::hash` + `WitnessChain::fold_step`.
   - `fuzz_targets/artifact_hash.rs` — feeds arbitrary artifact bytes + digests into `cis_verify::artifact::check_artifact_hashes`.
3. `cargo +nightly fuzz build` — all three targets compile clean (release+debuginfo, 27.66s).
4. Smoke validation (NOT the pre-registered campaign): each target run for **20 s** (not 3600 s) under `systemd-run --user --scope -p CPUQuota=60% -p MemoryMax=400M` with `-rss_limit_mb=300`, chosen to fit this leg's light-lane ceiling rather than the plan's heavy-lane cap.

## Rule A/B note

No timing/throughput figures are reported from this box (Rule A) — `exec/s` numbers from libFuzzer
above are its own internal progress counters, not a performance claim, and are not to be quoted as
one; the numbers that matter here are counts (executions, new corpus units, crash/leak/timeout
files found = 0) and peak RSS, which is a memory bound, not a speed claim.
